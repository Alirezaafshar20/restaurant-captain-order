# نصب مویا روی Ubuntu 22.04

این راهنما برای یک سرور اختصاص‌یافته به مویا نوشته شده است. پیشنهاد عملی برای ساخت image روی سرور: حداقل ۲ هسته، ۴ گیگابایت حافظه و فضای آزاد کافی برای چند image و نسخهٔ پشتیبان. این اعداد حداقل قطعی محصول نیستند؛ مصرف واقعی به بار و اندازهٔ نسخه‌ها بستگی دارد.

## بار اول

سه فایل `setup-server.sh`، `enable-https.sh` و `deploy.sh` را همراه این راهنما به یک پوشهٔ دلخواه روی سرور انتقال دهید. در ترمینال همان پوشه:

```bash
sudo bash setup-server.sh
```

نصب‌کننده پیش‌نیازها را نصب می‌کند، IP عمومی، نام ورود و کلید OpenAI را می‌گیرد و رمز ورود تصادفی تولید می‌کند. کلید را در همان ورودی مخفی وارد کنید؛ داخل چت یا GitHub قرار ندهید. رمز ورود تولیدشده را نگهداری کنید. نصب مجدد تنظیمات موجود را بازنویسی نمی‌کند.

در پایان یک **کلید عمومی SSH** نمایش می‌دهد. آن را در [Deploy keys مخزن](https://github.com/Alirezaafshar20/moya-captain-order/settings/keys) با گزینهٔ Add deploy key ثبت کنید. گزینهٔ **Allow write access خاموش** بماند. این کلید فقط به سرور اجازهٔ خواندن همین مخزن خصوصی را می‌دهد؛ کلید خصوصی روی سرور می‌ماند.

در فایروال هتزنر و در صورت فعال بودن UFW، ورودی TCP پورت‌های **۸۰ و ۴۴۳** را باز کنید و پورت SSH خود را نگه دارید. Docker برنامه را فقط روی loopback منتشر می‌کند و پورت‌های ۳۱۰۱/۳۱۰۲ نباید عمومی شوند. اسکریپت فایروال یا سرویس‌های دیگر را حذف نمی‌کند.

سپس:

```bash
sudo bash enable-https.sh
sudo bash deploy.sh
```

برای HTTPS همان IP عمومی و ایمیل خود را وارد کنید. اسکریپت قبل از صدور گواهی، پذیرش توافق‌نامهٔ Let's Encrypt را می‌گیرد. درخواست گواهی مستلزم دسترسی اینترنت به پورت ۸۰ است. [Certbot 5.4 به بعد از گواهی IP با webroot پشتیبانی می‌کند](https://letsencrypt.org/2026/03/11/shorter-certs-certbot/). گواهی IP کوتاه‌مدت است؛ تمدید خودکار فعال می‌شود و پورت ۸۰ باید برای تمدید در دسترس بماند.

بعد از موفقیت، `https://IP-SERVER/` را باز کنید و با نام و رمز ساخته‌شده وارد شوید. HTTPS برای دسترسی میکروفون و صدای زنده هم لازم است. کلید API باید به مدل‌های تنظیم‌شده در حساب OpenAI شما دسترسی داشته باشد؛ موفقیت نصب به‌تنهایی تضمین‌کنندهٔ دسترسی یا اعتبار حساب OpenAI نیست.

## هر بار به‌روزرسانی

ابتدا تغییرات مورد نظر را روی کامپیوتر در Git ثبت کنید و سپس، در پوشهٔ پروژه:

```bash
npm run push:github
```

این دستور آزمون‌ها، بررسی نوع‌ها، ساخت نسخه و آزمون واقعی سرور را اجرا می‌کند، تغییرات ثبت‌نشده را رد می‌کند، سپس push و شناسهٔ remote را بررسی می‌کند. اطلاعات نادیده‌گرفته‌شده مثل فایل کلید عمداً ارسال نمی‌شوند.

روی سرور فقط همان اسکریپت را اجرا کنید:

```bash
sudo bash deploy.sh
```

برای اطمینان از انتشار دقیق همان نسخه‌ای که کامپیوتر تأیید کرده، دستور چاپ‌شده توسط `push:github` را استفاده کنید:

```bash
sudo bash deploy.sh --expect-sha FULL_40_CHARACTER_COMMIT_SHA
```

سرور فقط تغییرات **commit و push شده** را می‌بیند. هیچ اسکریپت سروری نمی‌تواند از تغییرات باقی‌مانده روی کامپیوتر شما باخبر شود. نتیجهٔ بررسی GitHub Actions نیز در بخش Actions مخزن دیده می‌شود؛ deploy همان بررسی‌های ساخت را مجدداً روی image اجرا می‌کند.

## چه چیزهایی قبل از انتشار کنترل می‌شود؟

1. قفل اجرا، اعتبار HTTPS و تنظیمات سرور.
2. دریافت موفق شاخه، بررسی سلامت Git و تطبیق شناسهٔ نسخه با GitHub و در صورت ارائه، `--expect-sha`.
3. استخراج کامل یک commit در پوشهٔ تازه؛ هیچ `pull` روی نسخهٔ سرویس‌دهنده انجام نمی‌شود.
4. نصب دقیق وابستگی‌های فایل قفل، آزمون‌ها، lint، بررسی TypeScript، ساخت و آزمون واقعی ذخیره/بازیابی سفارش.
5. نسخهٔ پشتیبان آنلاین SQLite، سپس آزمایش نسخهٔ جدید روی کپی مستقل داده‌ها.
6. راه‌اندازی نسخهٔ جدید کنار نسخهٔ فعال و بررسی پایگاه داده، API، منو، عکس و محدودیت دسترسی.
7. بررسی دوبارهٔ تغییر نکردن شاخه، تغییر مسیر Nginx، و ثبت نسخهٔ فعال؛ سپس توقف نسخهٔ قبلی.

اگر ساخت یا بررسی‌های پیش از تغییر مسیر ناموفق باشند، نسخهٔ فعال ادامه می‌دهد. اگر بررسی تغییر مسیر شکست بخورد، اسکریپت مسیر قبلی را برمی‌گرداند. قطع برق/توقف ناگهانی از طریق فایل journal در اجرای بعدی بازیابی می‌شود. این کنترل‌ها خطاهای استقرار را کم می‌کنند؛ تضمین نبودن همهٔ خطاهای منطقی محصول نیستند.

مهاجرت خودکار پایگاه داده فقط ساخت جدول و index جدید را می‌پذیرد. تغییر یا حذف جدول/ستون، بازنویسی داده و تغییر فایل مهاجرت قبلی، انتشار را متوقف می‌کند و به برنامهٔ مهاجرت جداگانه نیاز دارد. سازگاری رفتار نسخهٔ جدید با قبلی همچنان باید بررسی شود. هنگام خطا، backup به‌صورت خودکار روی دادهٔ زنده بازگردانی نمی‌شود تا سفارش تازه از دست نرود.

## افزودن دامنه یا تغییر کلید

بعد از تنظیم رکورد A دامنه به IP سرور:

```bash
sudo bash enable-https.sh
sudo bash deploy.sh
```

این بار نام دامنه را وارد کنید. گواهی جدید پیش از جایگزینی تنظیم TLS قبلی دریافت می‌شود. برای کلید یا مدل، فایل زیر را روی خود سرور ویرایش و دوباره deploy کنید:

```bash
sudo nano /etc/moya/app.env
```

فرمت `NAME=value` است؛ دور مقادیر کوتیشن نگذارید. این فایل اجرا نمی‌شود و محتویاتش مستقیماً به کانتینر داده می‌شود. نام ورود فقط حروف لاتین/عدد/خط تیره/زیرخط و رمز حداقل ۲۰ کاراکتر باشد. کلید و رمز را به‌عنوان آرگومان دستور یا در مخزن ثبت نکنید.

## نگهداری و عیب‌یابی

- دادهٔ پایدار: `/opt/moya/data/moya.sqlite` و فایل‌های WAL/SHM کنارش؛ این پوشه را حذف نکنید.
- نسخهٔ پشتیبان قبل از به‌روزرسانی: `/opt/moya/backups/`؛ این پشتیبان روی همان سرور است و در برابر حذف سرور کافی نیست. برنامهٔ پشتیبان رمزگذاری‌شده خارج از سرور و آزمون بازیابی برای بهره‌برداری واقعی لازم است.
- وضعیت نسخهٔ فعال: `/opt/moya/active.json`؛ نسخهٔ پیشین: `/opt/moya/previous.json`.
- فایل‌های منبع هر نسخه: `/opt/moya/releases/`؛ کپی آزمایش داده: `/opt/moya/preflight/`. این مسیرها می‌توانند اطلاعات مشتری داشته باشند و دسترسی root دارند. برای جلوگیری از پر شدن دیسک، نگهداری و پاک‌سازی آگاهانه لازم است؛ اسکریپت خودکار آن‌ها را حذف نمی‌کند.
- اسکریپت نصب اولیه وابستگی‌های سیستم را آماده می‌کند؛ وصله‌های امنیتی سیستم‌عامل همچنان باید منظم نصب شوند.
- گواهی: `sudo /snap/bin/certbot certificates` و `sudo systemctl status snap.certbot.renew.timer`؛ پس از نصب، یک بار `sudo /snap/bin/certbot renew --dry-run` را برای آزمون تمدید اجرا کنید.
- سلامت: `sudo docker ps`؛ نام کانتینر در active.json مشخص است. لاگ: `sudo docker logs --tail 100 CONTAINER_NAME`؛ تنظیم Nginx: `sudo nginx -t`.

اگر فقط تغییرات برنامه را به‌روزرسانی می‌کنید، اجرای deploy کافی است. اگر خود اسکریپت‌های استقرار تغییر کرده‌اند، نسخهٔ تازهٔ آن‌ها را از مخزن جایگزین فایل منتقل‌شده کنید و بعد اجرا کنید؛ اسکریپت در میانهٔ اجرا خودش را بازنویسی نمی‌کند.

نسخهٔ فعلی ورود مشترک مخصوص ارائه دارد و همهٔ نقش‌ها زیر همان حساب اجرا می‌شوند. جداسازی حساب کارکنان، QR عمومی امن و پشتیبان‌گیری زمان‌بندی‌شده باید قبل از بهره‌برداری عمومی اضافه شوند. داده‌های سایت قبلی خودکار به این سرور منتقل نمی‌شوند.
